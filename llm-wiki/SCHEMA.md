# SCHEMA.md｜抽卡玩家權益 LLM Wiki 的維護規則

給維護這個 Wiki 的 LLM（Claude、Codex 等）看的規則。每次 ingest、query、lint 前先讀這份。
做法參考 Andrej Karpathy 的 LLM Wiki 模式：raw 來源不改，LLM 負責把知識整理進 wiki，並持續更新。

## 1. 三層結構
| 層 | 位置 | 誰可以改 |
|---|---|---|
| 原始來源 | `raw/S#-*.md` | 只新增，不修改內容（每份記錄網址、發布者、日期、擷取重點） |
| Wiki | `wiki/*.md` | LLM 維護；人類審閱 |
| 規則 | `SCHEMA.md`（本檔） | 人類與 LLM 討論後修改 |

## 2. 頁面格式
- 每頁開頭 YAML：`title`、`summary`（一句話）、`sources`（S# 清單）、`updated`。
- 內文每一個事實句結尾都要標來源，例如 `（S2 壹、六）`。**沒有來源的句子不准寫**；推論要標「推論：」。
- 數字、日期、金額必須和 raw 一字不差（例：30 日、200 元、180 日、3 萬～30 萬元）。
- 用 `[[頁面名]]` 互相連結；每頁至少連到 1 個其他頁。
- 來源之間有衝突或看似衝突時，寫進該頁「⚠ 衝突與待確認」段落，不要自己選一邊吞掉。
- 讀者是「第一次課金的大學生」：術語第一次出現就用一句白話解釋。
- **壓縮成白話時，條件詞不可刪**（run-01 的教訓）：「扣除必要成本」「每次」「經限期改正」「未使用」「第一次先通知」這類詞一定要跟著數字一起出現；「推論」「待確認」的內容在簡報上也要保留不確定的語氣。

## 3. 三種操作
- **Ingest**（一次一份來源）：讀 raw → 跟人類確認重點 → 更新或新增相關頁（通常 3～6 頁）→ 更新 `index.md` → 在 `log.md` 加一行。
- **Query**：先讀 `index.md` 找頁，再讀頁面回答；答案要附頁面與來源。好的答案存回 wiki（例如 `常見迷思.md`）。
- **Lint**：跑 `python tools/check_wiki.py`，檢查缺來源、壞連結、孤兒頁、raw 沒有的數字；再人工找衝突與過時說法。

## 4. 產生簡報的流程（run-01 後修訂）
取得資料 → Ingest → **檢查 A（lint）** → 查詢 Wiki → 整理大綱 → **檢查 B（大綱對照 Wiki，事實＋條件詞）** → 產生簡報 → **檢查 C（check_slides.py＋投影機／手機版面）**。
事實檢查放在**大綱階段**做，不要等簡報做完才查；簡報階段只重查數字、條件詞和版面。

## 5. 範圍
- 只整理**臺灣**法規與主管機關資料。
- 不給個案法律意見；簡報與頁面要提醒「實際爭議請洽 1950 或消保官」。
- 新聞只寫改寫摘要，不貼全文。
